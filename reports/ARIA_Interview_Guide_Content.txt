02 | PROJECT OVERVIEW

The project in 90 seconds

<b>Suggested explanation:</b> "ARIA brings four finance-related workflows into one conversational interface. A React frontend calls a FastAPI backend. Every question goes through a shared pipeline that normalizes the text, binds the user and conversation context, routes to a domain module, checks grounding and prepares the response for text or voice. Personal-finance calculations and equity valuations are computed in Python; language models mainly explain the results. SQLite stores user state and reports, while FAISS supports semantic concept retrieval. Optional voice and avatar services reuse the same answer path."

The central design decision

Keep structured data and numerical computation separate from natural-language presentation. An LLM response is not the source of truth for a price, ratio, financial profile or valuation. Source coverage and guard strength vary by route; they do not provide a universal factual guarantee.

Three pipelines to distinguish

&#8226; <b>Online serving:</b> a question becomes a contextual, grounded answer.

&#8226; <b>Data ingestion:</b> files, quotes, statements, concepts and headlines become validated structured records.

&#8226; <b>Offline learning and validation:</b> generated datasets or historical data produce model artifacts, backtests and measured evidence.

03 | DRAW THIS IN THE INTERVIEW

System architecture

The arrows summarize dependencies. Data providers feed the domain modules; persistence is shared infrastructure rather than a mandatory final step of every provider call.

Deployment topology

Development normally runs Vite on port 5173 and FastAPI on port 8000, with browser requests proxied to the API. The backend is a modular monolith: domain packages share one core application rather than independently deployed microservices. Optional avatar services run separately; forecast validation jobs can spawn isolated child processes.

<b>Why this shape?</b> It keeps a student-scale application easy to run and lets all channels reuse the same logic. The costs are shared process resources, tight deployment coupling and state that needs extra work before horizontal scaling.

Follow-up example

A user requests research on TCS and then asks, "What about its debt?" Conversation memory and company focus help resolve the reference. The system should use the resolved company and fetched statements rather than answering with an isolated generic definition of debt.

Retry behavior

A successful repeated request_id can return the saved response. Reusing the id for a different message is an error. This is request-level replay, not a promise of exactly-once execution across every external side effect or deployment topology.

<b>Observability:</b> qa.answer logs channel, mode, route, correction, grounding, degradation and stage timings. total_ms captured in response metadata and the final log timer can differ because they are sampled at different points.

05 | THE USER-DATA PIPELINE

Data ingestion and statement imports

Canonical transaction contract

The parser emits date, merchant, positive amount, debit/credit direction and category. The storage mapping translates profile categories such as rent to housing and health to medical. Credits and expenses must remain distinct so income is not counted as spending.

Why preview and atomic import matter

A preview exposes parsing problems before persistence. The import stores a receipt and reuses it on retries. SQLite writer serialization protects deduplication across overlapping previews and processes. A failed transaction should not leave only half the profile or transaction changes saved.

Quality controls and limits

The parser bounds rows, spreadsheet expansion, archive members, sheet count, cell count and PDF processing. Unsupported or ambiguous inputs produce warnings or errors. Do not describe this as a general OCR pipeline: image-only scans need a separate extraction capability.

<b>Sources:</b> modules/finance/statement_import.py; shared/statement_store.py; shared/user_store.py; tests/finance/test_statement_durability.py.

06 | FROM PROFILE TO COMPUTED ADVICE

Personal-finance inference

<b>Inputs:</b> facts supplied in chat or the profile wizard, persisted transactions, income, age, dependents, EMI, assets, liabilities, goals and other known profile fields. Stored defaults are not necessarily user-confirmed facts; sources metadata tracks what is actually known.

Two complementary computation paths

<b>Profile-aware deterministic engine:</b> computes net worth, financial-health components, goal funding, affordability, retirement/FIRE and what-if results from available facts. When a required fact is missing, the finance flow can ask a specific clarification.

<b>Model orchestration:</b> the structured finance orchestrator combines risk classification, spending forecasts, anomalies, constrained budgeting, tax computation and SIP allocation before asking the shared language-model client for narration.

Illustrative example, not a measured result

For monthly income Rs. 100,000 and EMI Rs. 15,000, debt-to-income is 0.15. This value is a feature, not the complete risk decision. The system should derive the remaining features from the user's actual history rather than inventing transactions.

How to defend the data choice

Synthetic data makes controlled experiments possible without collecting sensitive household histories. It also creates a substantial realism limit: a classifier can learn the generator's personas, and good synthetic performance does not establish real-world suitability. DQN rewards in a simulator do not establish improved student learning.

Evaluation points to discuss

For a future stronger evaluation, hold out users for risk classification, use chronological splits for forecasting, fit preprocessing inside the training fold, and compare against simple baselines. Report macro-F1 / calibration for classification, MAE / quantile loss / interval coverage for forecasts, and independently measured learning gains for tutoring. These are evaluation proposals, not scores measured for this PDF.

08 | RETRIEVAL + MASTERY + TEACHING POLICY

Adaptive tutor and semantic retrieval

What makes this retrieval-based?

The retriever returns concept metadata from a curated finance knowledge base. It is semantic concept retrieval rather than unrestricted search over the internet. Low-confidence matches are rejected; the tutor pipeline can fall back to a conversational LLM response when no concept or local resource is available.

Similarity equation

For normalized vectors q and d: similarity = q dot d = cosine(q, d). FAISS IndexFlatIP performs exact inner-product search over stored vectors. The current small concept collection does not require a distributed vector database.

Adaptive behavior

The orchestration maps estimated mastery to explanation depth. The policy can choose a teaching action and request a quiz. Recording a quiz answer appends a correctness interaction, recomputes mastery and saves the learning state for later turns. A mastery probability is a model estimate, not a certified assessment of competence.

The valuation explanation to practise

A DCF forecasts free cash flow, discounts it and bridges enterprise value to equity value per share. WACC, terminal growth and other configured inputs are assumptions, not facts discovered by the LLM. Sensitivity tables and bull/base/bear cases expose how assumptions change the answer. A bank needs a different model because debt and capital have a different economic role.

Important limits

A provenance ledger improves auditability; it cannot make an upstream statement correct. FinBERT sentiment is an optional local component. Evidence gaps, stale sources, currency mismatches or absent data must remain explicit. Persisting a report may fail separately from computing it; the code can still return an unsaved report.

10 | EXTERNAL AND HISTORICAL DATA

Markets, news and forecast validation

Market and news ingestion

Market analysis gathers real instrument / index context and uses it to ground the explanation. The repository integrates yfinance, screener.in for company statements, mfapi.in and AMFI for mutual-fund data, and RSS feeds for news. Provider coverage varies by workflow. Quote timestamps and market closures matter: "live" does not guarantee exchange-grade real-time data.

News is fetched, merged, deduplicated and ranked. Relevant headlines can be added to time-sensitive answers. Caching reduces repeated provider calls, but it creates a freshness tradeoff and must not hide a provider outage or stale snapshot.

Forecast-validation data flow

&#8226; Retrieve and quality-check historical bars; record gaps, duplicate observations, outliers and corporate-action concerns; cache histories as Parquet where applicable.

&#8226; Construct historical features and forward log-return targets for configured horizons: 1, 5, 21, 63 and 126 bars.

&#8226; Run walk-forward evaluation with purging / embargo controls. Fit imputation, scaling and model selection only on allowed training observations.

&#8226; Compare candidates with baselines, select through validation and require confirmation on an untouched test segment. Permit "no_model_beats_baseline" and "insufficient_evidence" outcomes.

&#8226; Persist run metadata, progress and results. A FIFO worker dispatches jobs to spawned child processes so timeouts can terminate expensive work.

Do not confuse two meanings of forecast

<b>Valuation scenarios</b> project operating assumptions into cash flows and fair value. <b>Statistical return forecasts</b> evaluate historical predictability against baselines. A plausible cash-flow story does not prove that the share price is predictable.

Availability constraint

Automatic forecast and scenario jobs are skipped in account mode by the research pipeline, and integrations with unsafe shared global state are restricted. Do not present all optional compute features as universally enabled for signed-in users.

<b>Sources:</b> shared/news.py; modules/market/; modules/equity_research/forecast/{data,features,backtest,selection,models,jobs,contracts}.py; scenario_backtest/.

Authentication versus identity

Private mode uses a browser/device owner id for local workflows; that id is not proof of a logged-in account. Account mode adds cookie-based authentication, password hashing and optional configured Google sign-in. The backend binds requests to the authenticated owner and checks ownership rather than trusting an arbitrary browser-supplied identifier.

Concurrency and failure handling

In-process session locks serialize conversation work for a session. The database supports durable records. Statement imports also acquire a database writer transaction before deduplication. These protections have different scopes: an in-memory lock alone does not coordinate multiple backend processes.

The LLM client supports Groq with Gemini fallback. QA handling turns provider errors into controlled degraded responses. A number-matching guard can remove unsupported figures on supported evidence routes; finance engine output may be tagged rather than rewritten. Source interpretation, nonnumeric claims and all subtle contradictions remain outside any simple numeric check.

12 | PRESENTATION OVER THE SAME ANSWER

Voice, avatars and latency

Common flow

Speech recognition or a text message produces a query. The shared QA pipeline produces a written answer. Presentation code can create a shorter spoken version, synthesize audio and send it to a browser or an avatar integration. Mode and channel affect presentation; they should preserve the underlying answer and owner scope.

[['Path', 'How to explain it'], ['Text / conversational UI', 'Written answer; audio presentation can be prepared separately.'], ['Live Avatar', 'Browser recognition, shared answer pipeline, spoken text and local Piper speech; browser face or 3D presentation.'], ['Local avatar engine', 'Optional engine service with chunking, audio/video framing, motion and supported rendering backends.'], ['LiveTalking', 'Optional separate lip-sync service and WebRTC presentation path.'], ['Tavus', 'Optional hosted conversational-video integration; availability depends on configuration and account-mode restrictions.']]

A useful latency decomposition

End-to-end latency = recognition / input time + queue and warm-up time + domain data fetch + computation + LLM narration + speech synthesis + transport and browser buffering. Measure time to useful text, first audible word and sustained playback separately.

Measured evidence and its limits

docs/MEASUREMENTS.md records partial measurements from 22 October 2026. Its browser avatar comparison uses a mocked chat reply and cached spoken text; it is not a complete chat-to-speech benchmark. It records GPU contention when both avatar services speak together, and some end-to-end measurements were still pending. Cite its setup and limitations if discussing those results.

Failure and interruption

Optional rendering services can become unavailable while chat remains usable. Interrupting server generation does not automatically remove audio already buffered in a WebRTC client. Correct barge-in needs both cancellation upstream and management of client playback / queued media.

What to measure before making performance claims

&#8226; Routing accuracy on independently labeled finance, tutor, market, equity and general questions.

&#8226; Model performance on held-out users or chronological future data, with baseline comparison and confidence intervals.

&#8226; Provider failure rate, cache age, p50/p95 request latency, active sessions, memory use and GPU contention.

&#8226; Grounding precision/recall, unsupported claims that slip through, and owner-isolation behavior across channels.

Proposed production evolution: not implemented architecture

Keep the API stateless by moving process-local coordination and shared session state to suitable shared infrastructure. Move long-running forecasts and GPU rendering behind explicit worker queues with cancellation and resource limits. Use a shared transactional database and object storage for durable artifacts, version schemas and model files, and add provider health/freshness metrics.

Introduce distributed coordination only where measured concurrency requires it. Do not add Kafka, Spark, Airflow or a microservice fleet simply to make the diagram larger: the present system is an application pipeline with local jobs and provider fetching, not a distributed lakehouse or streaming ETL platform.

14 | PRACTISE ALOUD

Interview questions and short answers

<b>Why not send every question directly to an LLM?</b><br/>Profiles, calculations and valuations need structured inputs, reproducible arithmetic and persistent state. Domain tools compute results; the model helps explain them.

<b>Is ARIA a RAG application?</b><br/>The tutor retrieves semantically matched concepts with Sentence-BERT and FAISS. Other modules mainly use structured data and deterministic tools. The whole system is broader than one document-RAG pipeline.

<b>Why XGBoost and LSTM?</b><br/>XGBoost fits tabular risk features; the spend LSTM models temporal category patterns. That rationale still needs baseline evaluation: a complex model must demonstrate a useful improvement.

<b>What happens if a model or provider is missing?</b><br/>Behavior is route-specific: the tutor can use a conversational fallback, optional sentiment can be absent, and provider/LLM failures are surfaced through warnings or controlled degraded answers. Not every failure has an equivalent-quality fallback.

<b>How do you prevent hallucinations?</b><br/>Use fetched structured evidence, code-based calculations, provenance labels, audits and route-specific numeric checks. These reduce unsupported claims; they do not prove every sentence true.

<b>How do retries avoid duplicate data?</b><br/>Completed chat requests can replay by request_id. Statement imports separately use persisted previews, deduplication, writer serialization and an atomic import receipt.

<b>How do you avoid time-series leakage?</b><br/>Separate past training observations from future evaluation, purge overlapping targets, use an embargo and fit preprocessing inside each training split. Select using validation and confirm on untouched test data.

<b>What is the biggest limitation?</b><br/>Synthetic finance/training data and external-source quality limit real-world claims. Optional integrations and process-local state also constrain deployment scale.

<b>How would you scale it?</b><br/>First measure the bottleneck. Isolate heavy jobs, externalize shared state and coordination, strengthen database/artifact operations, and add observability before splitting services.

<b>What did you personally build?</b><br/>Name the exact modules you owned, trace one input to output, explain a difficult bug or tradeoff, and report only results you actually measured.

<b>Final rehearsal:</b> Draw the UI -> API -> QA pipeline -> four modules -> storage/providers diagram. Trace one uploaded statement and one research request. Then explain synthetic-data limits and one production improvement in your own words.
