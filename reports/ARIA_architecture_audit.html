ARIA: what it actually is, versus what it should stay

A full trace of the repository as it exists today — every claim below is backed by a file and, where useful, a line number. No refactors, no deletions, no new code. Just the truth of the system, and where the complexity earns its keep.

Repo ARIA_CLEAN Branch chore/production-readiness Python files audited ~65 Method full read of every module + 2 live runtime probes

01

Executive Summary

ARIA is further along than the brief for this audit assumes, and its worst problem isn't over-engineering — it's disconnection. The deterministic finance tools are genuinely excellent. Two of the six trained ML models are real, correctly wired, and still functionally frozen in the live product because a UI feature to feed them real interaction data was never built. A handful of files are dead weight left over from an earlier scaffold. And the avatar — the thing this audit was nominally worried about being over-built with Wav2Lip/SadTalker/LivePortrait stacks — is in fact the single most disciplined piece of the whole codebase.

The central finding, stated once here because it recurs through half of this document: Module 1 (finance) and Module 2 (tutor) each contain a working, trained, correctly-orchestrated ML component that the live chat UI never actually feeds. Module 1's LSTM spend-forecaster and Isolation-Forest anomaly detector need transaction history; the chat pipeline always calls them with an empty transaction list (modules/finance/pipeline.py:232), because there is no UI flow to enter transactions. Module 2's DKT mastery tracker and DQN teaching-policy need quiz-answer history; the chat pipeline generates a real quiz item via a real LLM call whenever the DQN chooses ask_quiz, and the Streamlit UI never renders it or wires an answer back to modules/tutor/orchestrator.py:76 record_answer() — confirmed by grep, there is no such call anywhere in interface/streamlit_app.py. Both models are real thesis-grade work sitting one missing widget away from actually mattering.

Everything else is closer to what you'd hope: the XGBoost risk model, the LP budget optimizer, the tax engine, the SIP/EMI calculators, Module 3 (market) and Module 4 (equity research) all run on real data through real code paths every single time. The LLM is used correctly — for narration and light extraction, never for arithmetic. The test suite (50 tests) mocks the LLM properly and tests real deterministic behavior, not implementation details. And the avatar is a free, self-hosted, browser-native 3D lip-sync system with no GPU dependency and no API key, exactly matching your stated product vision — the Tavus CVI integration (added and hardened this session) is a clearly-marked, opt-in, paid alternative sitting behind its own UI toggle, not a replacement.

The cut list in §21 is short and concrete: two genuinely broken files, two dead stubs, one dead general-purpose module, and one config block that documents a device this project never actually asks a GPU to touch. Nothing on it is a trained model, a routing rule, or a UI surface. The bigger lift this audit surfaces isn't cutting — it's closing the two feedback loops above, which is design and UI work, not new ML.

Current System Architecture

There is no FastAPI/Flask backend behind the core product — Streamlit is the whole application layer, calling Python functions directly. This is a legitimate, deliberate choice for a single-process demo app, not a shortcut that needs justifying — see §12. The one place a real HTTP server exists is the optional Tavus CVI bridge, which is intentionally separate.

interface/streamlit_app.py (UI: 3 tabs — Chat / Your Profile / Your Progress) │ │ _handle_query(query, session_id, mode) ▼ core/orchestrator.py handle_query() │ ├─ mode == "Conversational Mode" → query rewrite via ai/llm (self-contained follow-up) │ ├─ core/router.py: is_equity_research_query() ─────► modules/equity_research/pipeline.py (Module 4) ├─ core/router.py: is_broad_market_query() ─────► modules/market/pipeline.py (Module 3) ├─ core/router.py: route_query() == "finance" ────► modules/finance/pipeline.py (Module 1) ├─ core/router.py: route_query() == "tutor" ────► modules/tutor/pipeline.py (Module 2) └─ else ────► generic ai/llm/groq_client narration Every module pipeline funnels through ai/llm/groq_client.generate_response() (Groq openai/gpt-oss-120b → Gemini gemini-3.6-flash fallback, both wrapped, never raises) core/session.py — ephemeral, in-process chat turn history (lost on restart) shared/user_store.py — persistent SQLite: FinancialProfile (M1), LearningState (M2)

The one deviation from a clean layered model: core/router.py's precise Module 3/4 predicates (is_equity_research_query, is_broad_market_query) are checked before the coarse route_query() bucket, with a comment at core/orchestrator.py:47-52 explaining exactly why (the coarse keyword classifier's MARKET_KEYWORDS list doesn't cover terms like "nifty"/"sensex"). This isn't architectural debt — it's a documented, deliberate ordering fix. Flagged here only because the brief asked to identify "incorrectly coupled" flows, and this is the one place routing logic isn't a single clean waterfall; it is, however, correctly explained in the code itself.

04

Request / Data / Execution Flows

Text request flow

streamlit_app.py text input → _handle_query() (reloads pipeline modules so local edits apply without restarting Streamlit, then calls) → core/orchestrator.handle_query() → router dispatch → module pipeline → ai/llm/groq_client.generate_response() for narration → render_response() parses the Insight/Analysis/Recommendation/Risk (or tutor's Cognitive/Functional/Causal) sections into styled cards. This is a real, traceable, single path — not the deep multi-hop flow the brief speculatively diagrammed.

Voice request flow

st.audio_input → ai/speech/stt.transcribe() (Whisper) → the transcript is written into the same text box (st.session_state.query_text) → from there it's identical to the text flow. Voice is a transcription front-end bolted onto the text pipeline, not a parallel system — which is the right design, not a shortcut.

Finance Tutor flow — as designed vs. as it runs

As designed (modules/tutor/orchestrator.py:31-73): query → SBERT+FAISS concept retrieval → DKT mastery lookup → DQN teaching-action choice → level-appropriate TAXAL explanation → optionally a quiz → user answers → record_answer() updates mastery → next turn reflects it.

As it actually runs in the live Streamlit app: query → retrieval → DKT (always reads empty history, so always returns all-zero mastery) → DQN (evaluates a state that never changes) → explanation at level 1 → quiz generated by a real LLM call → quiz silently discarded (confirmed: no "quiz" key is ever read anywhere in streamlit_app.py) → the loop never closes. See §6 for the full trace.

Personal Finance flow — as designed vs. as it runs

As designed (modules/finance/orchestrator.py:32-118): profile + transaction history → XGBoost risk → LSTM 3-month category forecast → Isolation Forest anomaly scan → LP budget optimization → SIP plan → tax → LLM narration grounded in all of the above.

As it actually runs: modules/finance/pipeline.py:232 always constructs UserFinancialInput(..., transactions=[]) — there is no chat flow, form, or upload path anywhere in the UI that ever populates transaction history. XGBoost still gets a meaningful prediction (its profile-only features — income, age, dependents, debt-to-income, city tier — are always populated; only the transaction-derived features zero out, per the explicit comment at modules/finance/features.py:52-58). LSTM forecast and Isolation Forest both explicitly early-return degenerate output when there's no transaction data (forecast_model.py:150-159 returns all-zero forecasts; anomaly.py:23,55-56's MIN_TRANSACTIONS = 10 guard means detect_for_user always returns []).

Avatar flow

Text response → ai/llm/audio_script.generate_audio_script() (a second, short LLM call that rewrites the answer into a 20–30s spoken script) → ai/speech/tts.synthesize() (edge-tts, pyttsx3 fallback) → interface/avatar/render.build_avatar_html() base64-embeds the audio into a self-contained HTML page → st.components.v1.html() → the browser's WebGL context runs TalkingHead's phoneme-driven lip-sync entirely client-side. No server-side video generation, no GPU, no per-frame rendering pipeline — see §11.

Broad-market / equity data flow (already real, not hypothetical)

The brief frames financial news and equity research as future work with only an interface to design for. Both already exist as working pipelines: modules/market/analyzer.py pulls live Nifty/Sensex/sector data via yfinance plus market-wide headlines via Economic Times' public RSS feed (no API key — explicitly chosen over NewsAPI's free tier, which forbids this use per the comment at analyzer.py:1-9); modules/equity_research/ pulls per-company fundamentals by scraping screener.in and live price/news via yfinance. See §18 and §19.

05

Personal Finance Assistant Audit

Financial understanding & personalization

Persisted per-user in shared/user_store.py's FinancialProfile table: income, age, dependents, existing EMI, emergency-fund months, city tier, tax regime, plus the latest risk label/confidence. This is genuinely minimal and well-chosen — no over-collection. Extraction from free text is a deliberately layered regex approach in modules/finance/pipeline.py: _parse_indian_amount() (lines 86–117) handles lakh/crore/k Indian numeric shorthand with word-boundary guards specifically added after two documented false-positive bugs ("emi" matching inside "premium", "earn" matching inside "learn" — see the inline comment at line 92-94), and _try_build_financial_profile() (lines 200–232) merges new-turn values with the saved profile using explicit is not None checks (not truthy checks) so a legitimate "I earn 0 now" doesn't get silently discarded by a falsy-value bug — also explicitly commented (lines 208-209, 215-217). This is the correct approach for a system this size: pure regex, deliberately, with the reasoning left in the code. No LLM-based structured extraction exists or is needed here — the domain (Indian salary/EMI phrasing) is narrow enough that regex is both more reliable and drastically cheaper than a model call per turn.

Financial calculations — deterministic, correctly separated from the LLM

Every number a user sees is computed in plain Python before the LLM ever runs, and the LLM's system prompt for narration explicitly forbids inventing values (M1_NARRATION in ai/llm/prompt_templates.py:43-82: "Use ONLY the numbers provided below. Do NOT invent any values."). This is exactly the principle the brief asks to verify — it already holds:

  • Risk profile — real trained XGBoost classifier, not a rule (§7)
  • Budget — real linear program via scipy.optimize.linprog, not the 50/30/20 rule as a hardcoded split (modules/finance/budget_optimize.py) — the 50/30/20 rule is explicitly the starting point the LP is built to override when infeasible, per the module docstring
  • Tax — closed-form Indian slab computation, both regimes, with Section 87A rebate and marginal-relief smoothing (modules/finance/tax.py:57-68) — slabs sourced and dated live against four tax sites (comment at lines 4-9)
  • SIP/EMI — standard closed-form annuity formulas (modules/finance/sip_emi_calc.py)

None of this is embedded in prompts. The LLM's only job on the numeric side is turning a filled-in template into readable Indian-English prose.

Risk profiling, specifically

Real trained XGBoost multiclass classifier (modules/finance/risk_model.py), not a hardcoded formula — five profile features plus (when available) sixteen transaction-derived features (features.py:15-32), SHAP-explained top contributing factors per prediction (with a documented never-raise fallback if SHAP itself fails, risk_model.py:49-65). Per your project roadmap notes, this scored 0.99 macro-F1 in 5-fold CV on synthetic data. It is deterministic given its inputs, personalized to whatever profile fields exist, and — critically — is the one of the three finance ML models that stays meaningful even with zero transaction history, because its most important features (income, age, EMI-to-income) are always populated. This is the finance module's best-designed piece.

Central finding — restated with full evidence

The LSTM spend forecaster and Isolation Forest anomaly detector are real, correctly trained, correctly wired — and functionally inert in the live product, because nothing in the Streamlit UI ever collects a user's transaction history. modules/finance/pipeline.py:232 hardcodes transactions=[] on every call. forecast_model.py:150's own docstring says it plainly: "Falls back to an all-zero forecast (no ML) if there's no transaction history at all." anomaly.py:23's MIN_TRANSACTIONS = 10 guard means detect_for_user returns [] unconditionally in the live app. Both models train and evaluate correctly offline (per your roadmap: LSTM MAE 2.3% of income, Isolation Forest caught 15/15 injected anomalies on synthetic data) — the gap is entirely in the interface layer, not the models. See §21 for the fix, which is a UI feature, not a model change.

Finance Tutor Audit

One correction to the brief's own framing before the audit: what's implemented is Deep Knowledge Tracing (Piech et al. 2015 — an LSTM over one-hot concept/correctness sequences, modules/tutor/knowledge.py:20-44), not classical Bayesian Knowledge Tracing (which would be a per-concept 4-parameter HMM). They solve the same problem — mastery estimation from an interaction sequence — but DKT is the more modern, higher-capacity approach and is what the code, the class name, and the training script (modules/tutor/train/train_lstm_kt.py) actually implement. Worth knowing precisely, since "BKT" and "DKT" get used interchangeably in casual conversation about this kind of system but are different models with different guarantees.

Retrieval

Real Sentence-BERT (all-MiniLM-L6-v2) + FAISS cosine search over a 50-concept knowledge base (modules/tutor/retriever.py), gated by an empirically-tuned similarity threshold (config/settings.py:79-82: "genuinely off-topic queries score ≤0.23, misspelled-but-real finance queries score ≥0.41" — a threshold chosen from data, not guessed). Below threshold, the pipeline correctly falls through to a generic tutor prompt instead of forcing a bad concept match. This is real, live, and load-bearing on every tutor query — no gap here.

DKT (mastery)

Real trained LSTM, correctly called from modules/tutor/orchestrator.py:40 on every tutor turn. But its input is the user's persisted interaction history (shared/user_store.get_learning_state), and that history can only grow via record_answer() — which nothing in interface/streamlit_app.py ever calls (confirmed by grep across the whole file: zero matches for record_answer). Every real user's mastery vector is permanently the cold-start default (knowledge.py:101-104: all-zero when history is empty) in the shipped product today.

DQN (teaching-action selection) — real RL, not decorative, but starved of state

This is genuinely a trained stable_baselines3.DQN policy (modules/tutor/teaching.py), trained via self-play against a simulated tutoring environment (no external dataset — modules/tutor/train/train_dqn_teacher.py), evaluated to a mean reward of 3.75 against a >0 target per your roadmap notes. State: [mastery_target, avg_mastery_prereqs, last_5_accuracy, session_length, concept_difficulty]; six actions (simplify / example / quiz / deepen / analogy / prerequisite). This is a real, non-trivial application of RL to an actual decision (not an RL system bolted on for demo value with no real choice attached to it) — the honest caveat is that because mastery_target and last_5_accuracy never move off their cold-start defaults in the live app (see above), the policy is currently always evaluating close to the same state vector, so its trained variety of behavior is not visible to a real user, even though the policy itself is real and was genuinely trained to handle a range of states.

Rebuild, not remove

The fix here is small relative to the models it unlocks: a quiz-answer widget in the Chat tab (radio buttons over QuizItem.correct_answer + wrong_answers, already fully generated and already flowing through the response dict at modules/tutor/pipeline.py:38) that calls modules.tutor.orchestrator.record_answer(user_id, concept_id, is_correct) on submit. That one widget makes DKT and DQN — both already real, already trained, already wired everywhere else — actually observable and actually adaptive for a real user. This is the single highest-leverage change surfaced by this entire audit.

TAXAL explanation & quiz generation

Both are thin, well-scoped LLM calls with strict parsing (modules/tutor/explainer.py, modules/tutor/quiz.py) — level-appropriate (1–8) via TAXAL_LEVEL_HINTS/TAXAL_LENGTH dictionaries in ai/llm/prompt_templates.py:17-37, further styled by the DQN's chosen action via TAXAL_ACTION_STYLE_HINTS (lines 110-117). quiz.py's parser returns None on malformed LLM output rather than crashing or fabricating a quiz — good defensive design.

08

LLM / AI Architecture Audit

One LLM client, one call surface, used everywhere: ai/llm/groq_client.generate_response(prompt, system_prompt). Every one of the four modules imports this single function — there is no per-module LLM wrapper duplication, no scattered client instantiation. This is the "LLM abstraction → provider → model" shape the brief asks for, already built, just without formal provider classes: a plain function with an internal two-tuple _BACKENDS list (groq_client.py:129) that tries Groq then Gemini in order.

Provider & fallback design

Two providers, not more (no Ollama, no local FinGPT, no third cloud provider — the original PDF plan's local-LLM idea was explicitly and correctly dropped per your roadmap notes, since it needed ~14GB VRAM this project doesn't have and can't assume for public deployment). The fallback chain is exactly two deep, wrapped so a caller can never see an unhandled exception — generate_response always returns a string, prefixed "Error: ..." on total failure, which interface/streamlit_app.py:116-125's render_response specifically detects and turns into a clear user-facing banner instead of leaking a raw error string into the chat. This is not excessive fallback logic — it's the minimum needed for "a free-tier API might rate-limit" to not mean "the demo breaks," and it's exactly two providers, not a chain of five.

One real, current bug found and fixed live during this session (not part of this audit's read-only scope, but material to note): both DEFAULT_MODEL_NAME (Groq) and DEFAULT_GEMINI_MODEL had drifted to retired model IDs as of today. Both providers' hosted catalogs move fast enough that hardcoded model-ID defaults are a genuine, recurring maintenance surface — worth a periodic live check, not a one-time fix.

Is this actually agentic?

Partially, and it says so honestly rather than dressing up prompt engineering as agency. What's genuinely present: real tool use (deterministic finance calculators, real yfinance/screener.in data fetches, real vector retrieval), real state (SQLite profile + mastery, session chat history), and one real closed-loop decision system (the tutor's DQN choosing an action from live-ish state). What's not present: the LLM itself never chooses which tool to call — that decision is made entirely by core/router.py's deterministic keyword/regex predicates before the LLM is ever invoked. There's no LLM-driven planning step, no ReAct-style loop, no LLM function-calling. This is the right architecture for this product (a routed, tool-augmented assistant), and it's honest to describe it as router + tools + state, not agent in the tool-calling-loop sense — using the more inflated label wouldn't survive a technical interview follow-up question, and the simpler true description is more defensible, not less impressive.

User State / Memory Audit

Two genuinely different, correctly separated memory systems exist — worth naming explicitly since nothing in the code currently calls out the split as a design decision:

Persistent — shared/user_store.py

SQLite (FinancialProfile, LearningState), keyed by session/user id. Survives restarts. Holds exactly the minimal fields the brief asks for: income, age, dependents, EMI, emergency-fund months, city tier, tax regime, risk label (M1); per-concept mastery + interaction history (M2). No overcollection.

Ephemeral — core/session.py

A single in-process dict[str, dict] (_SESSIONS). Chat turn history only. Lost on every restart, and — because it's keyed purely by whatever session_id a caller passes — shared across any two callers that happen to pass the same id. In the main Streamlit UI this is safe: each browser tab gets a fresh uuid4() (streamlit_app.py:480-481, with a comment confirming this is deliberate for concurrent visitors). It was not safe in the Tavus bridge before this session's fix, which hardcoded a shared session_id="tavus" for every conversation — now changed to read history from the request's own message list instead of touching this store at all.

Minimal state is already the reality here, not a target to migrate toward. The one thing worth documenting (not fixing) is that ephemeral chat history and persistent structured profile were never explicitly designed as a two-tier memory system — they just ended up that way, correctly, through two different modules solving two different problems.

Realistic Talking Avatar Audit

This is the part of the brief most worth correcting against the actual repository: there is no LivePortrait, MuseTalk, Wav2Lip, or SadTalker anywhere in this codebase, and there never has been per the git history. The avatar is TalkingHead — a browser-native, WebGL-rendered, VRM-rigged 3D model with phoneme-driven lip-sync, loaded from jsdelivr's CDN at runtime (MIT licensed, no API key — interface/avatar/NOTICE.md). This is a fundamentally different, and for this project's constraints, correct category of technology: not video generation, not a diffusion or GAN-based talking-head model, but a real-time 3D rig animated by audio — closer to VTuber tooling than to deepfake-style avatar synthesis.

Real-time classification

TalkingHead is genuine real-time streaming, not pre-generated or generate-on-demand — the browser animates the 3D rig live against the audio waveform the moment it's embedded; there is no server-side video render step at all, which is precisely why it needs no GPU and imposes no per-response latency cost beyond LLM narration + TTS synthesis. This is the most practical possible answer to "realistic, convincing, demonstrable, not maximum model complexity" — the brief's own stated goal — and it already exists exactly as specced.

Modularity

interface/avatar/render.py's build_avatar_html() takes only a response's audio path as input and returns self-contained HTML; it has zero imports from modules/, core/, or shared/. Swapping the avatar out would touch only interface/streamlit_app.py's rendering branch (currently gated on turn.get("mode") == "Conversational Mode", streamlit_app.py:400) — finance logic, tutor logic, and the LLM layer are provably untouched by an avatar swap, which is exactly the modularity principle the brief asks to verify. The Tavus integration proves this in practice: it was added as a third, fully independent mode ("Tavus CVI Mode (WebRTC)") without modifying a single line of core/ or modules/.

API Audit

There is no REST API surface for the core product — Streamlit calls Python functions in-process. Security Audit

  • Secrets handling — real API keys live only in a gitignored .env; .env.example documents every key with no real values. No key is hardcoded in source. Good.
  • No timeout on outbound scraping calls — screener_adapter.py:63,68 (see §15). Not exploitable by a third party, but a legitimate availability risk (one slow upstream page hangs a user's session).
  • The Tavus FastAPI bridge has no authentication (tavus_llm_server.py) — it binds 0.0.0.0:8000 and is tunneled publicly via ngrok for the duration of a session. Anyone who obtains the ngrok URL while it's live could POST to /v1/chat/completions and get free, unauthenticated completions routed through your Groq/Gemini keys. Low real-world risk given ngrok URLs are random and short-lived per session, but worth knowing this is an open relay while it's running, not a private one.
  • Web scraping fragility, not a security issue but adjacent — screener_adapter.py parses screener.in's HTML structure directly (section id="profit-loss" etc.); any layout change on their end silently degrades to empty data (handled gracefully — get_screener_data catches and returns {"error": ...} — but worth knowing this is inherently a brittle integration, structurally, not a bug).
  • No PII logging found — loguru calls throughout log query text and computed numbers, not names/emails/financial account identifiers, since none of those are ever collected in the first place.
  • CORS / auth — not applicable to the Streamlit app itself (no separate frontend origin); not configured on the Tavus bridge, consistent with the "no auth" point above.

Future Finance News Architecture

This is not a green-field design problem — modules/market/analyzer.py already answers a version of "what happened in the market today": get_index_snapshot() (Nifty/Sensex level + 5-day trend via yfinance), get_sector_snapshot() (equal-weight sector basket trend), and get_market_news() (live headlines via Economic Times' public RSS, explicitly chosen over NewsAPI because NewsAPI's free tier forbids this exact use — a real, considered decision, not an oversight). What's genuinely future work: a daily-digest framing ("summarize today" rather than "answer this specific question"), and possibly a scheduled/cached daily snapshot instead of computing on every request (currently lru_cached per-process, which resets on every Streamlit restart — fine for a demo, not for a always-on daily-briefing feature). AI/ML Value Assessment

Final Product Definition

ARIA is a conversational personal finance assistant for Indian users — grounded in real deterministic financial tools (risk profiling, budget optimization, tax computation, SIP/EMI math) and a real adaptive tutor for financial literacy, narrated by an LLM that explains but never calculates, spoken and lip-synced through a free, self-hosted, browser-native 3D avatar with an optional higher-fidelity paid video mode, extended today — not someday — with real live market data and real per-company equity research, and held together by one router that sends every question to exactly the module built to answer it correctly.

Brutally Honest Final Verdict

You asked whether this has become over-engineered and hard to maintain. It hasn't, in the way you were worried about — there is no zoo of avatar technologies, no five-deep LLM fallback chain, no microservice sprawl, no ML bolted on for demo credibility. The actual system is smaller, cleaner, and more disciplined than the audit brief's own brainstormed component list suggested it might be. The Wav2Lip/SadTalker/MuseTalk/LivePortrait avatar-stacking scenario you asked me to check for doesn't exist in this repository, full stop.

What you actually have is a well-bounded four-module assistant where two modules (finance, tutor) each contain one real, trained, correctly-integrated ML capability that the interface never finishes connecting to — not because it's hard, but because a UI feature (transaction entry; quiz answering) was never built to close the loop. That's a smaller, more specific, and considerably more fixable problem than "this is too complex, cut things." The complexity you have is mostly earned; a handful of files are dead weight from an earlier iteration and cost you nothing to remove; and the highest-value next move isn't subtraction at all — it's two modest UI features that would make four already-real trained models visibly, demonstrably adaptive in front of an evaluator, instead of quietly frozen at their cold-start defaults.
