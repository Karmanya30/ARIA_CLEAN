# Implementation C/D/E: LangGraph and the structured hybrid

## LangGraph inspected
`langgraph` 1.2.19 (MIT). `StateGraph` with a typed state, conditional edges, `Send` fan-out for parallel nodes, per-node retry policy, checkpointers. Checkpointing was not used: ARIA already persists conversations per turn (`core/session.py`), and a second persistence layer would duplicate it.

## Components
1. **Structured understanding** (`core/intent/understanding.py`, schema in `schema.py`): one bounded call (temperature 0, 8 s timeout) returns a strict Pydantic object: primary and secondary intents, objective, a standalone query, typed entities, required capabilities, sub-queries (at most 4, each with its intent), context references, missing information, ambiguities, a clarification flag and question, and three confidences (intent, entity extraction, context resolution). The provider's strict mode requires every object closed and no free-form maps (found when the first schema was rejected), so entities are a list of `{kind, value}`. Output that fails validation, invents or drops a number, drops a negation, or asks for clarification without a question is discarded and the system falls back (never trusted as is).
2. **Semantic Router** on the standalone query (not the raw text, so a resolved reference is routed on what it means).
3. **Decision** (`arch.decide_structured`): clarify when the model asks or context resolution is below its threshold; clarify when intent confidence is low unless the router independently agrees; clarify when the model and a confident router disagree (two confident, different signals are a reason to ask, not to guess); otherwise route to the model's intent, with the sub-queries if there are several. If the model is unavailable the router acts alone only above its thresholds, else the baseline runs.
4. **LangGraph workflow** (`core/intent/graph.py`): `plan -> execute (loops over the parts) -> verify -> synthesise`, typed state, node trace returned as `intent_graph`. Each part is run by the existing ARIA pipeline (`_run_label` in the orchestrator calls the unchanged finance, tutor, market, equity, intelligence and lookup functions). `verify` runs the existing number check on each part's own evidence, because a merged answer has no single evidence set. `synthesise` joins the parts under headings with no model call, so it cannot add facts; a part that failed is reported as "I couldn't complete this part" instead of dropped. One bounded retry per part, only after an exception.
5. **Variants:** C uses rule-based splitting (a split happens only when both halves are real clauses that the existing rules place in different modules); D replaces the rule routing with structured understanding + router + graph; E keeps the rules first and calls the structured layer only when they cannot place the question.

## A finding that shaped the design: no parallel parts inside a turn
The first version fanned parts out in parallel (`Send`). It deadlocked: ARIA holds a re-entrant per-conversation lock for the whole turn, and every real pipeline reads the session, so a worker thread waits for a lock held by the thread that is waiting for it. The benchmark hung on the first multi-part question it met. The default is therefore sequential execution in the calling thread; `parallel=True` stays available for thread-safe handlers and is covered by a test, and a regression test reproduces the deadlock. Parallel production use needs thread-safe session state first.

## Fallbacks
Every new layer returns "no opinion" on any exception, timeout, invalid output or missing package, and `ARIA_QUERY_ARCHITECTURE=baseline` (the default) never imports them. Independent switches: `ARIA_SR_MODE`, `ARIA_INTENT_LLM=0`, `ARIA_INTENT_GRAPH=0`.
